# فريق المستجيب الأول - الجومة (First Responder Team - Al Joumeh)

نظام إدارة فريق الإنقاذ. الواجهة الأمامية React (Vite) باللغة العربية بالكامل (RTL)،
والخادم Express يخزّن البيانات في ملفات JSON محلية.

## البنية

```
rescue-system/
├── client/     تطبيق React (Vite + Tailwind)
└── server/     خادم Express + تخزين JSON محلي
```

## التشغيل لأول مرة

### 1) الخادم (Backend)

```bash
cd server
npm install
npm run seed     # ينشئ ملفات البيانات + مفتاح التشفير secret.key + مستخدم تقنية المعلومات الافتراضي
npm start        # يعمل على http://localhost:5000
```

بعد تشغيل `npm run seed` سيتم إنشاء:
- `server/data/*.json` — ملفات البيانات لكل وحدة (فارغة جاهزة للاستخدام)
- `server/secret.key` — مفتاح 256-bit عشوائي، **يُستخدم لتشفير كلمات المرور. لا تشاركه ولا تضعه في Git.**
- مستخدم تقنية معلومات افتراضي:
  - **اسم المستخدم:** `mohamad.khoder`
  - **كلمة المرور:** `Luna18122001`
  - (لاحظ أنه بدون مسافة في اسم المستخدم، لأن أسماء المستخدمين لا يمكن أن تحتوي على مسافات)

> ينصح بشدة بتسجيل الدخول وتغيير كلمة المرور من صفحة "ملفي الشخصي" بعد أول استخدام.

### 2) الواجهة (Frontend)

```bash
cd client
npm install
npm run dev       # وضع التطوير: http://localhost:5173 (يتصل تلقائياً بالخادم عبر proxy)
# أو للإنتاج:
npm run build      # ينشئ مجلد dist/ جاهز للنشر (يمكن تقديمه عبر أي خادم ثابت)
```

## نشر secret.key على كل جهاز مخوّل

بحسب متطلبات المشروع، لا يُخزَّن هذا الملف في نظام التحكم بالإصدار. على مسؤول تقنية المعلومات:

1. تشغيل `npm run seed` مرة واحدة على جهاز مركزي لإنشاء `secret.key`.
2. نسخ هذا الملف يدوياً إلى كل جهاز يشغّل الخادم (وليس المتصفح فقط)، مثلاً:
   - Windows: `C:\Users\<username>\Desktop\FirstRescue\secret.key`
3. يمكن تغيير مسار الملف عبر متغيّر البيئة `SECRET_KEY_PATH` عند تشغيل الخادم.

⚠️ إن فُقد هذا الملف أو تغيّر، ستصبح جميع كلمات المرور المخزّنة غير صالحة للتحقق (يجب حينها إعادة تعيين كلمات المرور من قبل تقنية المعلومات).

## الأدوار الثلاثة

| الدور | الصلاحيات الأساسية |

| **IT (تقنية المعلومات)** | كل الصلاحيات: إدارة المستخدمين، سجل التدقيق، النسخ الاحتياطي، الإعدادات |

## ملاحظات هامة حول التنفيذ الحالي

هذا النظام تأسيسي (foundation) متكامل وظيفياً ويغطي: المصادقة والأدوار، لوحة التحكم،
الأعضاء (قائمة + ملف تعريف كامل)، المهام (قائمة + تعيين الأدوار)، المخزون، الإعلانات،
إدارة المستخدمين، سجل التدقيق، الإعدادات والنسخ الاحتياطي/الاستعادة، والتقارير (تصدير CSV).

نقاط يمكن التوسّع بها لاحقاً حسب الحاجة:
- تصدير PDF/Excel احترافي للتقارير (حالياً CSV متوافق مع Excel)
- رفع الملفات الفعلي للمستندات/صور المهام (الواجهة الخلفية لتخزين البيانات الوصفية جاهزة)
- رسوم بيانية تفصيلية إضافية لملف العضو (تدريب، حضور)
- إشعارات تلقائية عند اقتراب مواعيد الصيانة/انتهاء صلاحية المستندات

## وحدة الخرائط (GIS)

تمت إضافة خريطة تفاعلية (Leaflet + OpenStreetMap، مجانية بالكامل بدون مفتاح API) تشمل:

- **الخريطة (`/map`):** عرض المهام والأعضاء والمخزون والمرافق والمخاطر كطبقات قابلة للتفعيل/الإخفاء، بحث عن موقع، تحديد الموقع الحالي، قياس المسافة، تصدير/استيراد GeoJSON، وضع ملء الشاشة، خريطة أساسية داكنة أو فاتحة.
- **المخاطر (`/hazards`):** تسجيل مخاطر وحوادث بموقع جغرافي ونطاق تأثير دائري (نوع، خطورة، حالة، درجة خطورة).
- **المرافق (`/facilities`):** نقاط اهتمام ثابتة (مستشفيات، مراكز قيادة، مناطق آمنة، نقاط تجمع، إلخ).
- **إضافة سريعة من الخريطة:** يمكن لـ IT/مسؤول العمليات تفعيل "وضع الإضافة" والضغط مباشرة على الخريطة لتسجيل خطر أو مرفق دون فتح نموذج منفصل.
- **إحداثيات اختيارية:** أُضيف زر "تحديد على الخريطة" لنماذج المهام والأعضاء والمخزون؛ أي سجل بدون إحداثيات ببساطة لا يظهر على الخريطة (لا يوجد حقل مطلوب جديد، لا حاجة لتحديث السجلات القديمة).
- **خريطة كثافة الاستبيان:** عند استيراد استبيان (من صفحة المهام) يمكن اختياريًا تعيين عمود "القرية/المنطقة"؛ يقوم الخادم بتحديد إحداثيات كل قرية فريدة تلقائياً، وتُعرض على الخريطة كدوائر ملوّنة بحسب عدد الردود ونسبة الموافقة.

**متطلب اتصال بالإنترنت:** البحث عن المواقع وتحديد إحداثيات القرى يعتمدان على خدمة OpenStreetMap Nominatim المجانية، وهي تُستدعى من **الخادم** (وليس المتصفح). يجب أن يكون الجهاز الذي يشغّل `server` متصلاً بالإنترنت لعمل هاتين الميزتين تحديداً؛ باقي النظام (بما فيه عرض الخريطة نفسها وكل الوحدات الأخرى) يعمل محلياً كما هو موصوف أعلاه. عند فشل الاتصال، تظهر رسالة خطأ واضحة بدلاً من تعطل الخادم.

**غير مُنفَّذ بعد (يتطلب بنية تحتية إضافية، أو مؤجل بحسب طلب لاحق):** تتبّع GPS الحي لأفراد الفريق، التنبيهات الجغرافية التلقائية (Geofencing)، تحسين المسارات (Routing)، طبقات الطقس/الأقمار الصناعية/الطائرات المسيّرة، والتحليلات المعتمدة على الذكاء الاصطناعي.



- كلمات المرور: PBKDF2 (210,000 تكرار) + salt عشوائي لكل مستخدم + مفتاح سري مشترك (secret.key)
- الجلسات: رمز عشوائي 256-bit، انتهاء صلاحية تلقائي بعد 20 دقيقة من عدم النشاط من جهة الخادم،
  و15 دقيقة من جهة الواجهة، بالإضافة لسقف 8 ساعات للجلسة
- سجل تدقيق كامل لكل عملية إضافة/تعديل/حذف/تسجيل دخول وخروج، مقصور على دور تقنية المعلومات
- التحقق من الصلاحيات يتم فعلياً على مستوى الخادم (وليس فقط إخفاء العناصر في الواجهة)

## نظام الصلاحيات المخصصة لكل مستخدم

بالإضافة إلى الأدوار الثلاثة الأساسية، يمكن لتقنية المعلومات الآن **منح أو سحب صلاحية أي ميزة من أي مستخدم بشكل فردي**، من صفحة "إدارة المستخدمين" ← أيقونة الدرع بجانب كل مستخدم.

- كل ميزة (الأعضاء، المهام، المخزون، المخاطر، المرافق، الإعلانات، التقارير، التقييمات، الاستبيانات، الخريطة) لها ثلاث مستويات لكل مستخدم: **لا شيء / عرض / إدارة**.
- القيمة الافتراضية لكل مستخدم تُشتق من دوره (IT = إدارة كاملة دائماً، مسؤول العمليات = إدارة لمعظم الميزات، مساعد = عرض فقط). يمكن لتقنية المعلومات تجاوز أي من هذه القيم لمستخدم معيّن دون التأثير على باقي من يحمل نفس الدور.
- **مستخدمو تقنية المعلومات لا يمكن تقييدهم** — هذا مفروض من الخادم وليس فقط من الواجهة.
- **إدارة المستخدمين وسجل التدقيق والإعدادات تبقى مقصورة على دور تقنية المعلومات فقط** وليست جزءاً من هذا النظام القابل للتخصيص، لمنع منح صلاحيات حساسة عن طريق الخطأ.
- كل تعديل على صلاحيات مستخدم يُسجَّل في سجل التدقيق.
- التحقق من الصلاحيات يتم على مستوى الخادم في كل طلب (وليس فقط بإخفاء الأزرار في الواجهة).

## النشر عبر الشبكة — الاعتبارات الأمنية

إذا تم استضافة هذا النظام بحيث يصل إليه أكثر من جهاز عبر الشبكة (وليس فقط localhost)، طُبِّقت الحمايات التالية مسبقاً في الكود:

- **حماية من هجمات القوة الغاشمة**: حد أقصى 20 محاولة تسجيل دخول كل 15 دقيقة لكل عنوان IP، وحد عام 300 طلب/دقيقة على كل واجهة برمجة التطبيقات.
- **رؤوس أمان HTTP** عبر مكتبة Helmet (X-Content-Type-Options, X-Frame-Options، إلخ).
- **إبطال الجلسات تلقائياً** عند: تغيير كلمة المرور (يبقى الجلسة الحالية فقط)، إعادة تعيين كلمة المرور من قبل تقنية المعلومات، أو إيقاف الحساب — فوراً، وليس فقط عند انتهاء صلاحية الجلسة الطبيعية.
- **صور ومستندات الأعضاء محمية بتسجيل الدخول** — لم تعد ملفات ثابتة مفتوحة، ولا يمكن الوصول إليها بدون جلسة نشطة، وأسماء الملفات نفسها عشوائية بشكل غير قابل للتخمين (128-bit).

### يتطلب إعداداً منك قبل النشر عبر الشبكة

**1. HTTPS (الأهم).** بدون ذلك، تُنقَل بيانات تسجيل الدخول ورموز الجلسات عبر الشبكة كنص واضح. خياران:
   - **الأفضل:** ضع الخادم خلف وسيط عكسي (reverse proxy) مثل nginx أو Caddy مع شهادة Let's Encrypt مجانية — هذا هو الأسلوب المعتاد والأسهل صيانة.
   - **بديل مباشر:** شغّل الخادم نفسه عبر HTTPS بدون وسيط، بتحديد مسار الشهادة والمفتاح:
     ```bash
     SSL_CERT_PATH=/path/to/cert.pem SSL_KEY_PATH=/path/to/key.pem npm start
     ```

**2. إذا استخدمت وسيطاً عكسياً (nginx/Caddy)**، فعّل `TRUST_PROXY` حتى تظهر عناوين IP الحقيقية في سجل التدقيق بدلاً من عنوان الوسيط:
   ```bash
   TRUST_PROXY=true npm start
   ```
   ⚠️ لا تفعّل هذا إن لم يكن هناك وسيط فعلي أمام الخادم — يمكن للعميل عندها انتحال عنوان IP الخاص به.

**3. راجع دور "IT" لكل من يملكه** — هو الدور الوحيد الذي لا يمكن تقييده، وله وصول كامل لكل شيء بما فيه سجل التدقيق والنسخ الاحتياطي.

## النشر المركزي — خادم واحد لجميع المستخدمين

بدلاً من تشغيل نسخة منفصلة من الخادم على جهاز كل مستخدم (وهو ما يجعل مزامنة البيانات بينهم شبه مستحيلة بأمان)، أصبح النظام مُعداً ليعمل كخادم واحد مركزي: يقوم Express بتقديم الواجهة الأمامية المبنية وواجهة برمجة التطبيقات معاً من نفس الأصل (origin)، ويتصل كل المستخدمين بهذا الخادم الواحد عبر متصفحاتهم. لا حاجة لتشغيل `npm run dev` على كل جهاز بعد الآن — فقط افتح رابط الخادم في المتصفح.

### لماذا ليس عبر مزامنة الملفات (Google Drive/Dropbox وغيرها)؟

أدوات المزامنة هذه لا تدعم القفل أو المعاملات (transactions) — إن عدّل شخصان سجلاً قريباً من نفس اللحظة، يُفقد أحد التعديلين بصمت بدل دمجهما أو تنبيه أي طرف. بما أن هذا النظام مبني على تعديلات متزامنة من عدة مستخدمين (مهام، تقييمات، مخاطر...)، هذا ليس احتمالاً نظرياً بل خطر حقيقي على البيانات. الحل الصحيح معماريّاً هو نسخة واحدة من البيانات يتحدث معها الجميع، لا عدة نسخ يُفترض أن "تتزامن".

### التشغيل محلياً بالنمط المُجمَّع (خادم واحد)

```bash
cd client && npm install && npm run build
cd ../server && npm install && npm run seed && npm start
```
افتح `http://localhost:5000` — ستجد الواجهة والـ API يعملان معاً من نفس المنفذ.

### متغيرات البيئة المتاحة

| المتغير | الوصف | القيمة الافتراضية |
|---|---|---|
| `PORT` | منفذ الخادم | `5000` |
| `DATA_DIR` | مسار تخزين ملفات JSON | `./data` |
| `UPLOADS_DIR` | مسار الصور والمستندات المرفوعة | `./uploads` |
| `SECRET_KEY_PATH` | مسار مفتاح التشفير | `./secret.key` |
| `TRUST_PROXY` | فعّله فقط إن كان الخادم خلف وسيط عكسي فعلي | `false` |
| `ALLOWED_ORIGIN` | نطاقات مسموحة إن شغّل المستخدمون الواجهة محلياً على أجهزتهم بدل فتحها من الخادم مباشرة — قائمة مفصولة بفواصل، مثال: `http://192.168.1.20:4173,http://192.168.1.31:4173` | (غير مفعّل — نفس النطاق فقط) |
| `SSL_CERT_PATH` / `SSL_KEY_PATH` | لتشغيل HTTPS مباشرة من Node بدون وسيط | (غير مفعّل) |

⚠️ **`DATA_DIR` و`UPLOADS_DIR` و`SECRET_KEY_PATH` يجب أن تشير إلى مساحة تخزين دائمة (persistent) عند النشر السحابي.** أغلب المنصات المجانية تمسح القرص عند كل إعادة تشغيل أو نشر جديد ما لم تُخصَّص مساحة تخزين دائمة صراحة.

### خيارات الاستضافة

**1. جهاز دائم التشغيل على شبكتكم المحلية (بدون أي تكلفة سحابية)**
إن كان الفريق يعمل غالباً على نفس الشبكة (مركز الفريق، شبكة واي فاي مشتركة)، أبسط وأرخص حل هو تخصيص جهاز واحد (حتى جهاز مكتبي قديم أو Raspberry Pi) ليبقى مشغّلاً دوماً كخادم، ويتصل الجميع به عبر عنوان IP الخاص به على الشبكة. لا يتطلب أي حساب سحابي، لكنه يعمل فقط عندما يكون المستخدمون على نفس الشبكة (أو عبر VPN).

**2. Fly.io (يقدّم مساحة تخزين دائمة مجانية حالياً)**
الأنسب إن احتجتم وصولاً من خارج الشبكة المحلية. بحثتُ في الخيارات المتاحة حالياً (2026) ووجدت أن معظم المنصات المجانية (Render، Railway) **لا تشمل تخزيناً دائماً في خطتها المجانية** — وهذا يعني فقدان بياناتكم عند كل إعادة تشغيل. Fly.io حالياً من المنصات القليلة التي توفر تخزيناً دائماً ضمن حصة مجانية حقيقية:

```bash
# 1) تثبيت أداة Fly (مرة واحدة)
curl -L https://fly.io/install.sh | sh

# 2) تسجيل الدخول (يتطلب حساباً وربما بطاقة ائتمان للتحقق، دون فرض رسوم ضمن الحصة المجانية)
fly auth login

# 3) من داخل مجلد المشروع rescue-system (حيث يوجد Dockerfile وfly.toml)
fly launch --no-deploy   # اختر اسماً فريداً للتطبيق عند السؤال، ولا توافق على إنشاء قاعدة بيانات

# 4) إنشاء مساحة التخزين الدائمة (مرة واحدة فقط) — غيّر الحجم إذا احتجت أكثر من 1GB
fly volumes create frt_data --size 1 --region iad

# 5) النشر الفعلي
fly deploy

# 6) بعد النشر، أنشئ المستخدم الافتراضي (مرة واحدة فقط) عبر الاتصال بالحاوية:
fly ssh console -C "npm run seed"
```
بعدها، رابط تطبيقكم سيكون بصيغة `https://<اسم-التطبيق>.fly.dev` — جاهز مباشرة عبر HTTPS.

⚠️ **الخطط والحصص المجانية تتغيّر باستمرار عبر جميع المزوّدين** — راجع صفحة تسعير Fly.io الرسمية قبل الاعتماد الكامل عليها، ولا تعتبر هذا الدليل ضماناً دائماً لبقاء الخدمة مجانية.

**3. البديل الاحتياطي: استضافة مدفوعة بتكلفة منخفضة**
إن لم تعد الخيارات المجانية متاحة أو كافية، فإن خطط البداية المدفوعة من مزوّدين مثل Render (تبدأ من حوالي 7$/شهرياً مع قرص دائم) توفّر استقراراً أعلى وبدون القيود المرتبطة بالخطط المجانية (مثل توقف الخادم بعد فترة خمول).

### ملاحظة أمنية أخيرة

لا يستطيع أي مهندس أن يضمن "صفر ثغرات" بشكل مطلق — هذا ليس ادعاءً واقعياً لأي نظام. ما تم فعلياً في هذا الإصدار:
- تقييد CORS وCSP للنطاق نفسه فقط بدل السماح المفتوح سابقاً
- منع تجاوز مُعرّف السجل (id) عبر الطلب عند الإنشاء (كانت ثغرة فعلية تسمح بتصادم السجلات)
- حماية تاريخ الإنشاء (createdAt/createdBy) من التعديل حتى عند تحديث السجل
- تحديد حجم النصوص المُدخلة ورفض المفاتيح الخطرة (`__proto__` وغيرها) في كل نقاط الإدخال المشتركة
- كل الحمايات من الجولة السابقة (تحديد معدل الطلبات، إبطال الجلسات عند تغيير كلمة المرور/الإيقاف، حماية الملفات المرفوعة بتسجيل الدخول) لا تزال فعّالة

فجوات معروفة متبقية (يمكن معالجتها في جولة لاحقة عند الحاجة): لا يوجد تحقق كامل من صحة نوع/بنية كل حقل في كل نموذج (schema validation)، ولا قفل حقيقي على الكتابة المتزامنة لملفات JSON نفسها (نادر الحدوث لكن غير مستحيل تحت حمل عالٍ جداً من نفس السجل بالضبط في نفس اللحظة).

## النشر على Render

### الطريقة الموصى بها (تحفظ بياناتكم فعلياً)

الخطة المدفوعة الأرخص (Starter، حوالي 7.50$/شهرياً شاملة القرص الدائم) هي **الوحيدة** التي تحل مشكلتنا فعلياً — الخطة المجانية لا تدعم قرصاً دائماً إطلاقاً، ما يعني مسح كل البيانات (سجلات JSON + الصور والمستندات المرفوعة) عند كل إعادة تشغيل أو نشر جديد، **بدون أي طريقة لمنع ذلك**.

1. ادفعوا المشروع إلى مستودع GitHub
2. من لوحة Render: **New +** ← **Blueprint**
3. اختاروا المستودع — سيقرأ Render ملف `render.yaml` الموجود في المشروع تلقائياً ويُعِدّ كل شيء (الخطة، القرص الدائم، متغيرات البيئة)
4. بعد اكتمال النشر، أنشئوا المستخدم الافتراضي عبر شل الخدمة من لوحة Render: `npm run seed`

بهذا الإعداد، الخدمة **لا تتوقف أبداً بعد 15 دقيقة أصلاً** — هذا التوقف خاص فقط بالخطة المجانية؛ الخطط المدفوعة تبقى نشطة دائماً بشكل مدمج، فلا حاجة لأي حل بديل.

### إن أردتم فعلاً البقاء على الخطة المجانية

أضفنا دعماً اختيارياً لإبقاء الخدمة "مستيقظة" عبر تنبيه ذاتي دوري (`KEEP_ALIVE=true` في متغيرات البيئة) — لكن اقرأوا هذا التحذير أولاً:

⚠️ **هذا لا يحل مشكلة فقدان البيانات إطلاقاً.** حتى مع منع التوقف بسبب الخمول، الخطة المجانية على Render لا تملك قرصاً دائماً، وقد يُعاد تشغيل الحاوية دورياً لأسباب أخرى (صيانة، تحديثات المنصة) بغض النظر عن التنبيه الذاتي — ما يمسح البيانات رغم ذلك. كما أن هذا الأسلوب **غير مدعوم رسمياً من Render** (وثّقنا هذا مباشرة من منتدى الدعم الرسمي لـ Render قبل بنائه). هذا الخيار يمنع فقط بطء الاستجابة الأول (cold start)، ولا يستبدل الحاجة الفعلية للقرص الدائم.

إن قررتم استخدامه رغم ذلك، فعّلوه بضبط:
```
KEEP_ALIVE=true
```
سيستخدم الخادم متغير `RENDER_EXTERNAL_URL` (يوفّره Render تلقائياً) لتنبيه نفسه كل 10 دقائق. للاختبار خارج Render، يمكن تحديد `KEEP_ALIVE_URL` يدوياً بدلاً منه.

## النشر على Oracle Cloud "Always Free" — دليل كامل

هذا خيار مجاني بشكل دائم (وليس تجربة تنتهي)، لكنه يتطلب إدارة خادم فعلي بنفسكم (Linux VM حقيقي، بصلاحيات root كاملة) — على عكس Render/Fly.io. الدليل هنا يفترض توزيعة Ubuntu، وهي الأسهل توثيقاً.

### 1) إنشاء الحساب
اذهبوا إلى `oracle.com/cloud/free` وسجّلوا حساباً جديداً. ستحتاجون لبطاقة ائتمان/خصم للتحقق من الهوية (حجز مؤقت فقط، لا خصم فعلي طالما بقيتم ضمن حدود Always Free). **اختاروا "Home Region" بعناية** — يصعب تغييره لاحقاً؛ اختاروا الأقرب جغرافياً لفريقكم.

### 2) إنشاء الخادم الافتراضي (VM)
من لوحة Oracle Cloud Console:
1. **Compute** ← **Instances** ← **Create Instance**
2. اسم الخادم: مثلاً `frt-rescue-server`
3. **Image**: اختاروا **Ubuntu** (أحدث إصدار LTS، مثل 24.04)
4. **Shape**: اضغطوا "Change Shape" ← **Ampere (ARM)** ← `VM.Standard.A1.Flex` — اختاروا عدد الأنوية والذاكرة ضمن الحدود المجانية (2 OCPU / 12GB مثلاً؛ إن ظهرت رسالة "Out of Capacity" جربوا منطقة أخرى قريبة أو أعيدوا المحاولة لاحقاً — هذا شائع مع هذه الفئة تحديداً)
5. **Boot Volume**: اتركوه على الحجم الافتراضي أو ارفعوه — المجموع الكلي المجاني 200GB عبر كل الأقراص
6. **SSH Keys**: اختاروا "Generate a key pair" وحمّلوا المفتاح الخاص (private key) فوراً — لن تتمكنوا من تحميله لاحقاً
7. تأكدوا أن "Assign a public IPv4 address" مفعّل، ثم **Create**

### 3) فتح المنافذ (Firewall) — خطوتان منفصلتان، كلتاهما ضرورية

**أ) من واجهة Oracle:**
Networking ← Virtual Cloud Networks ← (الشبكة التي أُنشئت تلقائياً) ← Security Lists ← Default Security List ← Add Ingress Rules:
- Source `0.0.0.0/0`، Protocol `TCP`، Destination Port `80`
- Source `0.0.0.0/0`، Protocol `TCP`، Destination Port `443`

**ب) من داخل الخادم نفسه** (صور Ubuntu على Oracle تأتي بجدار حماية مقيّد على مستوى النظام أيضاً، منفصل عن إعدادات Oracle أعلاه):
```bash
sudo iptables -I INPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT -p tcp --dport 443 -j ACCEPT
sudo netfilter-persistent save
```

### 4) الاتصال بالخادم
```bash
chmod 600 /path/to/your-downloaded-key.pem
ssh -i /path/to/your-downloaded-key.pem ubuntu@<PUBLIC_IP>
```
(عنوان IP العام تجدونه في صفحة تفاصيل الـ Instance)

### 5) تثبيت Docker
```bash
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
newgrp docker
```

### 6) نقل المشروع إلى الخادم
الأبسط: ادفعوا المشروع إلى مستودع GitHub خاص، ثم:
```bash
git clone https://github.com/<your-username>/<your-repo>.git rescue-system
cd rescue-system
```
(أو انسخوا الملفات مباشرة عبر `scp -i your-key.pem -r rescue-system ubuntu@<PUBLIC_IP>:~`)

### 7) بناء الحاوية وتشغيلها بشكل دائم
```bash
docker build -t frt-rescue .
mkdir -p ~/frt-data

docker run -d --name frt-rescue \
  --restart unless-stopped \
  -p 5000:5000 \
  -v ~/frt-data:/data \
  -e DATA_DIR=/data/app-data \
  -e UPLOADS_DIR=/data/uploads \
  -e SECRET_KEY_PATH=/data/secret.key \
  -e TRUST_PROXY=true \
  frt-rescue
```
`--restart unless-stopped` يضمن إعادة تشغيل الحاوية تلقائياً بعد أي إعادة إقلاع للخادم. المجلد `~/frt-data` على قرص الخادم نفسه — يبقى دائماً طالما لم تحذفوا الخادم.

### 8) إنشاء مستخدم تقنية المعلومات الافتراضي
```bash
docker exec -it frt-rescue npm run seed
```

### 9) اسم نطاق + HTTPS مجاني (Let's Encrypt)
تحتاجون اسم نطاق يشير إلى عنوان IP العام للخادم (سجل DNS من نوع A). إن لم يكن لديكم نطاق، يمكن استخدام خدمة نطاق فرعي مجانية مؤقتاً مثل `duckdns.org`.

```bash
sudo apt update && sudo apt install -y nginx certbot python3-certbot-nginx

# انسخوا الملف الجاهز من المشروع وعدّلوا YOUR_DOMAIN فيه
sudo cp deploy/nginx-oracle.conf /etc/nginx/sites-available/frt-rescue
sudo nano /etc/nginx/sites-available/frt-rescue   # استبدلوا YOUR_DOMAIN باسم نطاقكم الفعلي
sudo ln -s /etc/nginx/sites-available/frt-rescue /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# يضيف certbot إعدادات HTTPS تلقائياً ويجدد الشهادة دورياً
sudo certbot --nginx -d your-domain.com
```

### 10) تثبيت عنوان IP (منع تغييره عند إعادة الإقلاع)
من صفحة الـ Instance ← Attached VNICs ← IPv4 Addresses ← "Edit" على العنوان العام ← حوّلوه من Ephemeral إلى **Reserved** (مجاني طالما متصل بخادم Always Free نشط).

### 11) الاختبار
افتحوا `https://your-domain.com` — يجب أن تظهر صفحة تسجيل الدخول عبر HTTPS بشهادة صالحة.

### تحديث التطبيق لاحقاً
```bash
cd ~/rescue-system
git pull
docker build -t frt-rescue .
docker stop frt-rescue && docker rm frt-rescue
# أعيدوا تشغيل أمر docker run من الخطوة 7 — البيانات في ~/frt-data تبقى سليمة لأنها خارج الحاوية
```

## النشر على Google Cloud "Always Free"

نفس فكرة Oracle Cloud (خادم مجاني بشكل دائم، ليس تجربة مؤقتة)، لكن بمواصفات أصغر ونطاق ترافيك مجاني محدود جداً (~1GB شهرياً فقط) — يستحق الانتباه بما أن هذا التطبيق يعرض صوراً ومستندات الأعضاء، وهي أكثر ما يستهلك هذا الحد. راقبوا استهلاككم من لوحة Billing إن اخترتم هذا الخيار.

### 1) إنشاء الحساب
اذهبوا إلى `cloud.google.com/free`. سيُعرض عليكم رصيد تجريبي 300$ لمدة 90 يوماً — هذا منفصل عن "Always Free"؛ اقبلوه إن أردتم، لكن الخادم الذي سننشئه هنا يبقى ضمن الحصة المجانية الدائمة حتى بعد انتهاء تلك التجربة أو حتى دون تفعيلها.

### 2) إنشاء الخادم الافتراضي (VM)
من Console:
1. **Compute Engine** ← **VM Instances** ← **Create Instance**
2. الاسم: `frt-rescue-server`
3. **Region**: اختاروا واحدة **حصراً** من: `us-west1` (أوريغون) أو `us-central1` (آيوا) أو `us-east1` (كارولينا الجنوبية) — هذه الوحيدة المشمولة بـ Always Free
4. **Machine type**: `e2-micro`
5. **Boot disk**: اضغطوا "Change" ← تأكدوا من اختيار **Standard persistent disk** (وليس Balanced، الافتراضي عادة) — هذا شرط أساسي لتبقى ضمن الحصة المجانية ← اختاروا Ubuntu (أحدث LTS) ← الحجم حتى 30GB
6. تحت **Firewall**: فعّلوا **Allow HTTP traffic** و **Allow HTTPS traffic** (هذا ينشئ قواعد جدار الحماية اللازمة تلقائياً، على عكس Oracle حيث تُضاف يدوياً)
7. **Create**

### 3) الاتصال بالخادم
أبسط من Oracle — لا حاجة لإدارة مفاتيح SSH يدوياً: من صفحة الـ Instance، اضغطوا زر **SSH** المجاور له مباشرة، فيفتح طرفية (terminal) في المتصفح متصلة بالخادم فوراً.

(أو عبر أداة `gcloud` من جهازكم: `gcloud compute ssh frt-rescue-server --zone=<المنطقة>`)

### 4) تثبيت Docker

```

cd rescue-system
```

نفس الأمر بالضبط المستخدم مع Oracle — التطبيق والـ Dockerfile لا يتغيران بين المنصتين:
```bash

```

### 8) اسم نطاق + HTTPS مجاني
نفس خطوات Oracle بالضبط — استخدموا نفس ملف `deploy/nginx-oracle.conf` (لا علاقة له بمنصة معينة، هو إعداد nginx عام):

### 9) تثبيت عنوان IP (منع تغييره عند إعادة الإقلاع)
من **VPC Network** ← **IP addresses** ← بجانب العنوان الخارجي المرتبط بالخادم، اضغطوا **"Reserve Static Address"**. يبقى مجانياً طالما مرتبطاً بخادمكم النشط — يُفرض رسم صغير فقط إن حجزتموه دون ربطه بخادم فعلي.

راقبوا الاستهلاك من **Billing** ← **Reports** في لوحة التحكم. إن كان فريقكم يعرض صوراً/مستندات كثيرة، فكّروا بضغط الصور قبل الرفع، أو انتقلوا لاحقاً إلى Oracle Cloud (نطاق ترافيك مجاني أوسع بكثير) إن أصبح هذا الحد مقيّداً فعلياً.

## استضافة الواجهة على Netlify (مع خادم API منفصل)

**لا يمكن تشغيل الخادم (server/) على Netlify** — منصتها مبنية على دوال بلا حالة (serverless functions) بلا أي تخزين دائم بين الطلبات، وهذا التطبيق يعتمد بالكامل على تخزين ملفات JSON والمستندات/الصور المرفوعة على القرص. أي كتابة ستُفقد فوراً قبل الطلب التالي حتى.

لكن Netlify ممتازة لاستضافة **الواجهة فقط**، مقترنة بخادم API يعمل على Oracle Cloud أو Google Cloud (حسب الدليل أعلاه). الملف `netlify.toml` جاهز في المشروع لهذا بالتحديد.

### الخطوات
1. ادفعوا المشروع إلى GitHub
2. من لوحة Netlify: **Add new site** ← **Import an existing project** ← اختاروا المستودع (سيقرأ `netlify.toml` تلقائياً)
3. من **Site settings** ← **Environment variables**، أضيفوا:
   ```
   VITE_API_URL = https://your-domain.com   # رابط الخادم الذي أعددتموه على Oracle/Google Cloud
   ```
4. من جهة الخادم (على Oracle/GCP)، أضيفوا نطاق Netlify الذي سيُعطى لكم (مثل `your-site.netlify.app`، أو نطاقكم المخصص إن ربطتموه) إلى متغير البيئة:
   ```
   ALLOWED_ORIGIN=https://your-site.netlify.app
   ```
   ثم أعيدوا تشغيل حاوية الخادم لتطبيق التغيير
5. أعيدوا النشر على Netlify (Deploy)

بهذا الإعداد: Netlify تخدّم الواجهة مجاناً وبشكل مستقر تماماً (على عكس خيارات الخادم المجانية التي بحثنا فيها)، والبيانات الفعلية تبقى محفوظة بأمان على خادمكم على Oracle/Google Cloud.

## النسخ الاحتياطي التلقائي

سكريبت جاهز في `deploy/backup.sh` — ينسخ مجلد البيانات كاملاً (السجلات + الصور والمستندات + مفتاح التشفير) في أرشيف مضغوط، ويحذف تلقائياً أي نسخة أقدم من 14 يوماً (قابل للتعديل) حتى لا تمتلئ مساحة التخزين تدريجياً.

### الإعداد (مرة واحدة فقط)

```bash
chmod +x ~/FRT/deploy/backup.sh
crontab -e
```
أضيفوا هذا السطر في نهاية الملف الذي يُفتح (شغّل يومياً الساعة 2 فجراً):
```
0 2 * * * /home/YOUR_USER/FRT/deploy/backup.sh >> /home/YOUR_USER/backup.log 2>&1
```
استبدلوا `YOUR_USER` باسم المستخدم الفعلي على الخادم (نفس الذي يظهر في سطر الأوامر، مثال: `mmoudi821`). احفظوا واخرجوا.

**تحقق من الجدولة:**
```bash
crontab -l
```

### أين تُحفظ النسخ الاحتياطية

في `~/frt-backups/` — كل نسخة باسم يحمل التاريخ والوقت، مثل `frt-data-20260813-020000.tar.gz`.

### التحقق اليدوي (اختياري)

لتشغيل نسخة احتياطية فوراً دون انتظار الموعد المجدول:
```bash
~/FRT/deploy/backup.sh
```

### الاستعادة من نسخة احتياطية

```bash
docker stop frt-rescue
tar -xzf ~/frt-backups/frt-data-TIMESTAMP.tar.gz -C ~/restore-temp
# راجعوا محتوى ~/restore-temp/frt-data قبل الاستبدال، ثم:
rm -rf ~/frt-data
mv ~/restore-temp/frt-data ~/frt-data
docker start frt-rescue
```

⚠️ **نسخة احتياطية على نفس الخادم لا تحميكم من فشل الخادم نفسه بالكامل** (تلف القرص، حذف الحساب السحابي، إلخ). للحماية الحقيقية، انسخوا مجلد `~/frt-backups` دورياً إلى مكان مختلف تماماً (جهازكم الشخصي، أو Google Drive عبر رفع يدوي دوري) — نفس أسلوب التنزيل عبر زر "Download file" في نافذة SSH المستخدم سابقاً في هذا الدليل.
